# passkey-agent Agent Instructions

## Non-negotiables

- Surgical edits only: every changed line must trace to the request. No drive-by refactors, no reformatting untouched code, no deleting pre-existing dead code (mention it instead).
- Fix root causes. Never silence a warning, weaken a check, or patch a symptom to make a gate pass.
- Never report completion while any `just` gate below fails. Report the failure verbatim and stop.
- Stop and ask when a request is ambiguous, conflicts with existing conventions, or requires credentials, publishing, or destructive operations.
- When a correction reveals a missing rule, add one specific rule here ("always X for Y", never "be careful with Y"); delete rules that never catch real errors.

## Scope

- passkey-agent is a passwordless-first local credential agent and SOPS runtime environment. Core principles: biometric unlock, zero private-key persistence, automatic memory zeroization, side-channel resistance.
- `crates/pk-core` is the shared library: crypto primitives (`crypto.rs`), FIDO2 surface (`fido.rs`), the IPC protocol (`ipc.rs`), agent configuration (`config.rs`) and the SOPS creation rules (`sops_config.rs`).
- `bin/pk-daemon` is the background daemon (library plus the `pk-daemon` binary). It owns the `Locked`/`Unlocked` state, the 15-minute unlock TTL and the zeroizing key store.
- `bin/pk-cli` is the `pk` binary: it prompts the user, talks to the daemon over the Unix socket and `exec`s the requested command with `SOPS_AGE_KEY` in the environment (`decrypt`/`edit`/`encrypt` exec `sops` directly).
- The client and the daemon speak bincode over a Unix domain socket with a 4-byte little-endian length prefix. The protocol is defined once in `pk-core`; never fork it in a binary crate.
- Agent configuration lives at `~/.config/passkey-agent/config.json`.
- `docs/design.md` is the original architecture blueprint (written in Chinese) and `specs/` holds the per-feature design/task specs generated by `pb-improve`; `specs/README.md` carries the execution order and status table.
- English only in code, comments, docs, and commit messages. `docs/design.md` and `specs/2026-06-12-04-graceful-shutdown/design.md` are the only Chinese documents.

## Execution

- Parallelize aggressively: dispatch subagents for independent research, exploration, and implementation.
- NEVER run two `cargo` commands concurrently, and never overlap file edits with a running `cargo` command (`target/` file lock): finish edits, wait, then run.
- NEVER use `git worktree`. Edit the current branch in place.
- TDD for behavior changes: failing crate-local test first, smallest change to pass, then run `just mutation` and fix surviving mutants.

## Verification loop

After each feature or bug fix, in order; any failure means the task is not done:

```bash
just format
just lint
just test
just mutation
```

`just lint` is exactly the tool set CI installs: `typos`, `rumdl`, `taplo fmt --check`, `cargo +nightly fmt --check`, `cargo +nightly clippy --all -- -D warnings`, `cargo machete`.

## Workspace rules

- Never hand-type dependency versions. Add per-crate deps with `cargo add <crate> -p <crate>`. Shared deps go into root `[workspace.dependencies]` (numeric versions only, no default features) and are referenced with `dep = { workspace = true }`.
- Sub-crates inherit `version`/`edition`/`license`/`repository` via `workspace = true` and must set `[lints] workspace = true`.
- TOML formatting is `taplo` (CI installs `taplo-cli`, not `cargo-sort`); unused-dependency detection is `cargo machete` (CI installs `cargo-machete`, not `cargo-shear`). Do not introduce the other two tools here.
- There is no `rust-toolchain.toml`; CI installs a nightly toolchain, so use `cargo +nightly fmt` and `cargo +nightly clippy` exactly as the Justfile does.
- `allow_attributes` is `deny`: a bare `#[allow(...)]` is a hard compile error. `unwrap_used`, `expect_used`, `panic`, `todo`, `unimplemented`, `print_stdout` and `print_stderr` are denied too.
- `[workspace.package] repository` is still the placeholder `TODO`, so `just publish-check` cannot succeed yet. Fix that field before any release attempt.
- `authenticator`, `interprocess`, `ecdysis` and `config` are declared in `[workspace.dependencies]` but not wired into any crate. The `authenticator` line is commented out in `crates/pk-core/Cargo.toml` because it needs an NSS build dependency; `crates/pk-core/src/fido.rs` therefore returns `AuthenticatorUnavailable` and the FIDO2 `hmac-secret` path is a stub. Do not pretend that path works.

## Dependency choices

- Symmetric encryption: `chacha20poly1305` (XChaCha20-Poly1305) everywhere. It is side-channel resistant without AES-NI, which is why it is used instead of AES.
- Key derivation: `argon2` (Argon2id) for the password-derived KEK. The passkey-derived KEK is meant to come from the FIDO2 `hmac-secret` extension.
- Key hierarchy: a random 32-byte DEK encrypts the `age` private key; each KEK (passkey-derived and password-derived) encrypts the DEK. The DEK is the only thing held in memory.
- Secret handling: `secrecy` and `zeroize` in `bin/pk-daemon`, which is the only component that holds key material.
- Serialization: `bincode` for the IPC frames, `serde`/`serde_json`/`serde_yaml` for configuration.
- Async and IPC: `tokio`. The daemon uses `tokio::net::UnixStream` with the `net`/`io-util`/`time`/`sync` features plus `signal`; `pk-core` uses `net`/`io-util`/`time`. `interprocess` is not in use.
- Errors: `thiserror` in `pk-core` and in `pk-cli/src/error.rs`, `eyre` in the binaries. Never `anyhow`.
- Observability: `tracing` plus `tracing-subscriber` with `env-filter`. Never `log`.
- CLI ergonomics: `clap` (derive), `inquire` for prompts, `indicatif` for progress.
- No `reqwest`, no `hpx`, no `sqlx`, no `parking_lot`.

## Code conventions

- Zero private-key persistence: keys live only in the daemon's memory, are wrapped by the DEK, and the daemon zeroizes them when it locks or when the 15-minute TTL expires.
- The unlock TTL is a hard security property, not a convenience: `UNLOCK_TTL` in `bin/pk-daemon/src/state.rs` is 15 minutes and the check is `elapsed < UNLOCK_TTL`. Do not extend it without an explicit decision.
- The daemon is the only component that may hold plaintext key material. The CLI must ask the daemon over the socket and must never cache a key.
- Error variants must stay distinguishable so the CLI can map them to distinct exit codes; do not collapse a library enum into one bucket.
- `pk run` hands the process over with `exec`, so the CLI must not leave cleanup work after the exec.
- Property tests (`proptest`) are colocated in `pk-core` (`crypto.rs`, `ipc.rs`) and run in the ordinary `cargo test` path.
- Tests are colocated `#[cfg(test)]` modules in `crates/pk-core/src/**`; `pk-daemon` is a dev-dependency of `pk-core`, which is how the integration tests drive a real daemon.
